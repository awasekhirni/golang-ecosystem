## Versioning

- Source: git, trunk-based development.
- Module: `github.com/ori-inc/hexagonal-go`.
- Releases: semver `MAJOR.MINOR.PATCH`, tagged as `v1.2.3`.
  - MAJOR: backwards-incompatible API or schema change.
  - MINOR: new endpoint, new aggregate, new migration (additive).
  - PATCH: bug fix; no schema change.
- Docker images: `hexagonal-go:v1.2.3` and `hexagonal-go:latest` on each
  release; CI tags get `hexagonal-go:ci-<sha>`.

## Branching

- `main`: always deployable. Direct pushes forbidden; PR only.
- `develop`: integration branch for the next release. PRs from feature
  branches land here.
- `feat/*`, `fix/*`, `chore/*`: short-lived; deleted on merge.
- Hotfixes: branch from `main`, merge to both `main` and `develop`.

## Database schema (schema-as-code)

- Every schema change is a paired `*.up.sql` + `*.down.sql` under
  `internal/database/migrations/`, named `<seq>_<name>.{up,down}.sql`.
- The `seq` is `YYYYMMDDHHMMSS` (UTC) so ordering is unambiguous across
  developers.
- Migrations must be **forward-only compatible**: the new code must run
  against both the old and the new schema during a rolling deploy.
- Destructive changes (drop column, rename) are split across two releases:
  release N stops using the column; release N+1 drops it.

## Configuration sources (precedence high → low)

1. CLI flags
2. Environment variables (validated by envconfig at boot)
3. `.env` file (development only; never in prod)
4. Defaults baked into `config.Config`

## Secrets

- Never in git. Use sealed-secrets (k8s) or AWS Secrets Manager.
- The `JWT_SECRET` env var is validated at boot to be ≥32 bytes in prod.
